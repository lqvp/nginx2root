# CVE-2026-123633 — HTTP/2 reusable 接続の UAF（drain 時） 再現ノート

## 1. 概要

- 対象: nginx 1.31.8（脆弱） / 1.31.9（修正）
- 不具合: ストリームを持たない HTTP/2 接続が reusable キューに登録されたまま
  ストリームが生成されると、その接続が reusable のまま残る。upstream への接続要求で
  `ngx_get_connection()` が `ngx_drain_connections()` を呼び、drain が
  「ストリームを持っている自分の HTTP/2 接続」を close 対象に選ぶ。
  GOAWAY の送信に失敗すると `ngx_http_v2_finalize_connection()` で接続と
  リクエストのプールが解放され、その後の upstream 処理が解放済みメモリを使う (UAF)。
- 誘発条件: `worker_connections` が少なく、free_connection_n が connection_n/16 以下で、
  reusable キューに（ストリームを持ったままの）HTTP/2 接続が入っていること。
- 修正コミット: `2df48a5` "HTTP/2: reset reusable connection status on stream creation"
  （ストリーム生成時に `ngx_reusable_connection(c, 0)` を呼ぶ）。
  reusable 登録自体は `76672e650` 以降、部分フレーム受信時に DoS 回避のため行われる。

### 1.1 ソース上の根拠（1.31.8）

`src/core/ngx_connection.c`:

```c
void
ngx_drain_connections(ngx_cycle_t *cycle)
{
    ...
    if (cycle->free_connection_n > cycle->connection_n / 16) {
        return;
    }
    ...
    n = cycle->reusable_connections_n / 8;
    ...
    q = ngx_queue_last(&cycle->reusable_connections_queue);  /* 最も古い reusable */
    c = ngx_queue_data(q, ngx_connection_t, queue);
    c->close = 1;
    c->read->handler(c->read);
}
```

`src/http/v2/ngx_http_v2.c` の `ngx_http_v2_handle_connection()`:

```c
    if (ngx_reusable_connection(c, 1) != NGX_OK) { ... }

    if (h2c->state.incomplete) {
        return;      /* 部分フレーム: read handler は ngx_http_v2_read_handler のまま */
    }
```

ストリームを生成しても reusable 状態が解除されないため、drain に選ばれる。
1.31.9 では `ngx_http_v2_state_headers()` から
`ngx_reusable_connection(c, 0)` が呼ばれ、drain に選ばれない。

## 4. 再現手順

1. `18444` へ TLS (ALPN h2) で接続し、`PRI * HTTP/2.0...` プリフェイス + 空 SETTINGS を送る。
2. HEADERS フレーム（`END_STREAM|END_HEADERS`, sid=1）の先頭 1 バイトだけを送る。
   - nginx はフレームのヘッダすら未完成のためストリームを作らず、
     `ngx_http_v2_handle_connection()` で reusable 登録して早期 return する。
   - この接続は reusable キューの最も古いエントリになる。
3. `18445` へ HTTP/1 keep-alive 接続を 56 本張り、各接続で `GET /` を送って応答を読む。
   - リスナ 2 + HTTP/2 接続 1 + keep-alive 56 で free_connection_n が 4 になり、
     `free_connection_n > connection_n/16`（4 > 4 が偽）の drain 閾値に到達する。
4. 残りの HEADERS ペイロードを送り、直ちに `SO_LINGER(1,0)` で close（RST）。
   - ストリームが生成され、`proxy_pass` が upstream 接続を要求。
   - `ngx_get_connection()` → `ngx_drain_connections()` が最も古い reusable
     = 自分の HTTP/2 接続を `c->close = 1` にして read handler を呼ぶ。
   - HTTP/2 read handler は processing=1 を見て GOAWAY を送ろうとするが、
     クライアントは RST 済みのため送信に失敗 → finalize → 接続とリクエストを解放。
   - その後 upstream 処理が解放済みリクエストを使う → UAF / signal 11。
5. 1.31.9 ではストリーム生成時に reusable が解除されるため、drain は
   keep-alive 接続 (*3〜*9) を選び、HTTP/2 接続は生き残る → クラッシュしない。

`nkeep` は環境（ポート確認用の一時接続など）で 1 ずれるため、モジュールは
56, 55, 57, 54, 58 の順に試行する。

## 6. モジュールの使い方

```bash
python3 modules/123633.py build/inst-vuln/sbin/nginx  poc-run-B
python3 modules/123633.py build/inst-fixed/sbin/nginx poc-run-B
```

`run(binary, workdir, host="127.0.0.1")` は `{"cve","configured","trigger","effect","detail"}`
を返す。`effect` の判定:

- `CRASH`: `worker process N exited on signal 11` / `segmentation fault`
- `UAF`: `GOAWAY ... last sid 1`（ストリーム持ちのまま drain 再利用）があり、クラッシュは無い
- `TRIGGERED`: 同一経路を実行し drain も発動したが、HTTP/2 接続は再利用されずクラッシュも無い
- `ERROR` / `SKIP`: 起動失敗 / `nginx -t` 失敗

結果ファイル: `modules/123633.result.json`（1.31.8 / 1.31.9 の両方）。

## 7. 注意点

- drain の閾値は `connection_n/16`。worker_connections を 64 にしているため 4 本以下で発動する。
- reusable キューは先頭挿入・末尾取り出し（最も古いものから閉じる）。
  HTTP/2 接続を最初に reusable にしないと drain に選ばれない。
- ポート確認用の一時接続もスロットを 1 本使うため、keep-alive 本数は 1 本ずれる。
  モジュールは 56/55/57/54/58 を順に試す。
- 停止は pid ファイルの master へ `SIGTERM`、加えて `/proc` 走査で自 prefix の
  nginx のみを対象にする（pkill 不使用）。worker がクラッシュしても master が再起動する。
