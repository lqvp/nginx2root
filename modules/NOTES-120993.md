# CVE-2026-120993 — PROXY protocol v2 + 動的証明書の NULL 参照 (SIGSEGV) 再現ノート

## 1. 概要

- 対象: nginx 1.31.8（脆弱） / 1.31.9（修正）
- 不具合: stream で downstream の `listen ... ssl` に動的証明書（`ssl_certificate $var` +
  `ssl_certificate_cache`）を使い、upstream へ `proxy_protocol v2` を送る構成で、
  TLS セッション再開（abbreviated）した接続を処理する worker が SIGSEGV で落ちる。
- 修正コミット: `c4892ab` "Core: fixed segfault in PROXY protocol v2 with dynamic certificates"
  （`ngx_proxy_protocol_v2_ssl_sub()` の SIG_ALG / KEY_ALG 分岐で
  `SSL_get_certificate()` の戻り値 NULL チェック `if (cert == NULL) return NGX_DECLINED;` を追加）
- 類似修正: `5784889fb`（2019, OCSP stapling + 動的証明書の同型 NULL 参照）
- 1.30.x は対象外: PROXY protocol v2 **出力**（`proxy_protocol v2;` ディレクティブ）は
  1.31.4 で入った機能のため、vuln1306 / fixed1307 (1.30.6/1.30.7) には当該コードパスが無い。

### 1.1 脆弱性の仕組み

1. クライアントが TLS 1.2 でフルハンドシェイクすると、動的証明書コールバック
   `ngx_stream_ssl_certificate()` が走り、`SSL_get_certificate()` は leaf 証明書を返す。
   PROXY v2 の SSL TLV（SIG_ALG/KEY_ALG）生成は成功し、upstream へのヘッダは正常。
2. 同じセッションで再開（abbreviated）すると、サーバは Certificate メッセージを
   送らないため証明書コールバックが呼ばれず、`SSL_get_certificate()` が NULL のまま。
3. upstream 接続時に `ngx_proxy_protocol_v2_write()` → `ngx_proxy_protocol_v2_eval_ssl()` →
   `ngx_proxy_protocol_v2_ssl_sub()` の SIG_ALG 分岐が `X509_get_signature_nid(NULL)` を呼び、
   NULL+0x88 近傍の READ で SIGSEGV（KEY_ALG の `X509_get_pubkey(NULL)` も同型）。
4. 重要な点: TLS TLV は downstream（クライアント→nginx）側の `c->ssl` から作られるため、
   トリガーは「クライアント→nginx のセッション再開」である（upstream の種類は無関係）。

## 2. 環境

| 項目 | 値 |
|---|---|
| モジュール | `modules/120993.py`（自己完結・標準ライブラリのみ、`run(binary, workdir, host) -> dict`） |
| 脆弱版 | `build/inst-vuln/sbin/nginx` = nginx/1.31.8 → **CRASH (signal 11)** |
| 修正版 | `build/inst-fixed/sbin/nginx` = nginx/1.31.9 → **TRIGGERED（クラッシュせず）** |
| ASan 脆弱版 | `build/inst-asan-vuln/sbin/nginx` → **CRASH（ASan SEGV レポート＋signal 6）** |
| ASan 修正版 | `build/inst-asan-fixed/sbin/nginx` → **TRIGGERED（クラッシュせず）** |
| 作業ディレクトリ | `poc-run-G/cve-2026-120993`（prefix） |
| 専有ポート | downstream stream ssl **18451** / upstream 素の TCP **19011** |
| 結果ファイル | `modules/120993.result.json`（4 バイナリ分） |
| 実行時間 | 1 バイナリあたり約 5〜15 秒（1 ラウンド 3 接続、最大 3 ラウンド） |

証明書は `openssl req -x509 -newkey rsa:2048 -nodes` で module が毎回生成
（`server-default.pem/.key` と `server-second.pem/.key` の 2 種、**chmod 644**）。
conf で使うのは `server-default` のみ（`set $cert`/`set $key` 経由）。

ASan 版は worker が `nobody` 権限で動くため `logs/` を 777 にし、
`ASAN_OPTIONS=detect_leaks=0:abort_on_error=1:handle_segv=1:log_path=<logs>/asan`
でレポートをファイル出力する（#16 実績と同じ運用）。

## 3. 設定（モジュールが毎回生成）

`poc-run-G/cve-2026-120993/nginx.conf` の要点:

```nginx
worker_processes 1;
daemon on;
pid <rundir>/logs/nginx.pid;
error_log <rundir>/logs/error.log info;

events { worker_connections 256; }

stream {
    server {
        listen 127.0.0.1:18451 ssl;

        # TLS 1.2 に固定（abbreviated 再開を安定させる）
        ssl_protocols TLSv1.2;

        # 動的証明書（変数）+ キャッシュ
        set $cert <rundir>/certs/server-default.pem;
        set $key  <rundir>/certs/server-default.key;
        ssl_certificate $cert;
        ssl_certificate_key $key;
        ssl_certificate_cache max=10;

        # セッション再開を有効化
        ssl_session_cache shared:SSL:1m;
        ssl_session_timeout 10m;
        ssl_session_tickets on;

        proxy_pass 127.0.0.1:19011;
        proxy_protocol v2;          # ← ここで SSL TLV 生成が走る
    }
}
```

upstream（19011）は Python の `socketserver` で、PROXY v2 ヘッダ（128 bytes 程度）を
読み捨てて `UPSTREAM` を返すだけの素の TCP サーバ。

## 4. トリガ手順（クライアント）

Python `ssl` モジュール（`modules/120993.py` 内 `_run_round()`）:

1. `SSLContext(PROTOCOL_TLS_CLIENT)`、`check_hostname=False`、`verify_mode=CERT_NONE`、
   `minimum_version=maximum_version=TLSv1.2`、`server_hostname="default.example"`。
2. 1 接続目: フルハンドシェイク。`tls.session` を取得して保持。
   upstream から `UPSTREAM` が返る（正常系）。
3. 2 接続目以降: `ctx.wrap_socket(raw, session=前回の session)` で再開。
   脆弱版ではここで worker が SIGSEGV（クライアントは ConnectionResetError / 空応答）。
   ※ `SSLContext.session` への代入では再開しない。`SSLSocket.session` を次接続の
   `session=` 引数に渡すと `session_reused=True` になる。

## 5. 実行結果（`modules/120993.result.json`）

### 1.31.8 (vuln): CRASH

```
接続結果=[{'conn': 0, 'reused': False, 'data': b'UPSTREAM'},
          {'conn': 1, 'reused': True,  'data': b''},        ← ここでクラッシュ
          {'conn': 2, 'reused': False, 'data': b'UPSTREAM'}] ← worker 再起動後はフルハンドシェイクで正常
worker signal 終了=1 件 ['11']
クラッシュ例: worker process 188577 exited on signal 11
```

### 1.31.8 ASan (asan-vuln): CRASH

ASan レポート（`poc-run-G/cve-2026-120993/logs/asan.<pid>`、abort_on_error=1 なので
worker は signal 6 で終了）:

```
==188630==ERROR: AddressSanitizer: SEGV on unknown address 0x000000000088
==188630==The signal is caused by a READ memory access.
==188630==Hint: address points to the zero page.
    #0 X509_get_signature_nid (/lib/x86_64-linux-gnu/libcrypto.so.3+0x2f0140)
    #1 ngx_proxy_protocol_v2_ssl_sub src/core/ngx_proxy_protocol.c:957
    #2 ngx_proxy_protocol_v2_eval_ssl src/core/ngx_proxy_protocol.c:789
    #3 ngx_proxy_protocol_v2_write src/core/ngx_proxy_protocol.c:711
    #4 ngx_stream_proxy_init_upstream src/stream/ngx_stream_proxy_module.c:970
    #5 ngx_stream_proxy_connect_handler src/stream/ngx_stream_proxy_module.c:1874
```

アドレス `0x88` = NULL + オフセット 0x88 で、`X509_get_signature_nid(NULL)` による
NULL 参照であることが特定されている（NULL ページの READ）。

### 1.31.9 (fixed) / 1.31.9 ASan (asan-fixed): TRIGGERED

```
接続結果=[{'conn': 0, 'reused': False, 'data': b'UPSTREAM'},
          {'conn': 1, 'reused': True,  'data': b'UPSTREAM'},
          {'conn': 2, 'reused': True,  'data': b'UPSTREAM'}]
worker signal 終了=0 件
```

同一経路（フルハンドシェイク＋セッション再開）を実行してもクラッシュせず、
再開接続も upstream へ PROXY v2 ヘッダ付きで中継され `UPSTREAM` 応答が返る。

## 6. 判定ロジック（modules/120993.py）

- error.log の `worker process N exited on signal 11`（非 ASan）/
  `exited on signal 6`（ASan, abort_on_error=1）または `exited with code`、
  または `logs/asan.*` の AddressSanitizer SEGV レポートを検出 → CRASH, trigger=True
- クラッシュなし かつ 全接続で upstream 応答あり かつ `session_reused=True` あり
  → TRIGGERED（修正版の挙動。同一経路を実行したがクラッシュしない）
- `nginx -t` 失敗（例: 1.30.x で `proxy_protocol v2` が unknown directive）→ SKIP

## 7. 備考 / 限界

- 本モジュールは 4 バイナリ（vuln / fixed / asan-vuln / asan-fixed）のみ検証。
  1.30.x は `proxy_protocol v2` ディレクティブ自体が無いため対象外。
- `pkill` 不使用。master PID（pid ファイル）を保持して SIGQUIT → SIGKILL で停止。
- ASan 版実行時のみ `logs/` を 777 にする（worker が nobody で asan.<pid> を作るため）。
  非 ASan 版は通常の 755 のまま。
- クラッシュは worker のみ。master は worker を再起動するため、次の（フルハンドシェイクの）
  接続は再び成功する。継続的な再開接続を送り続ければ worker は繰り返し落ちる（DoS）。
- TLS 1.3 の PSK 再開でも同経路になるはずだが、Python ssl でのチケット受け渡しが
  不安定なため TLS 1.2 に固定して安定再現している。
