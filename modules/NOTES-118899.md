# CVE-2026-118899 — TLS 1.3 request body 読取中の NGX_AGAIN 無限ループ (PoC モジュール)

## 概要

- CVE: CVE-2026-118899
- 対象: nginx の TLS 1.3 通信において、request body 読取処理
  (`ngx_http_do_read_client_request_body()`) の内側のループが
  `c->recv()` の `NGX_AGAIN` を「読み取り準備未完了」として扱ってしまい、
  worker が 100% CPU でスピンする (無限ループ) 問題。
- **修正**: 1.31.9 の 2b129b93 「Request body: explicit handling of
  NGX_AGAIN.」(1.30.7 にもバックポート、HTTP/3 側は c51ffa2d)。
- **機構**: `ngx_ssl_recv()` は SSL_read() の `SSL_ERROR_WANT_WRITE` を受け
  取ると `c->write->ready = 0` を設定するだけで `c->read->ready` をクリア
  せず `NGX_AGAIN` を返す。外側の `while (c->read->ready)` が成立したまま
  なので recv を即座に再呼び出し、無限ループする。
- **成立条件**: nginx が request body を読んでいる最中に、SSL 層が
  「読み取りのために書き込みが必要」(`SSL_ERROR_WANT_WRITE`) を返すこと。
  TLS 1.3 の KeyUpdate (再鍵交換) 受信時の応答書き込みで発生し得る。

## モジュール

- `modules/118899.py` は自己完結型 PoC。`run(binary, workdir,
  host="127.0.0.1", spin_window=2.0, extra_patterns=None,
  debug_probe=True) -> dict`。`effect` は SPIN / TRIGGERED / ERROR / SKIP。
- 専有ポート 18452 (HTTPS TLS1.3)。作業ディレクトリは
  `/app/data/sessions/conv-43/poc-run-H` 系。
- クライアントは `ssl.SSLObject` + `ssl.MemoryBIO`
  (modules/123007.py のパターン流用)。KeyUpdate 注入は ctypes で
  `SSL_key_update()` + `SSL_do_handshake()` を直接呼び、生成された
  KeyUpdate レコード (暗号文 `1403030001` から開始) を任意タイミングで
  ソケットに送出する。`_SSLSocket` のオフセット 24 から SSL* を取得
  (本環境 Python 3.12.16 + OpenSSL 3.0.22 で `SSL_get_version ==
  b'TLSv1.3'` を確認済み)。

### nginx.conf (テンプレートから生成、 PREFIX 置換)

```nginx
daemon on;
worker_processes 1;
pid __PREFIX__/logs/nginx.pid;
error_log __PREFIX__/logs/error.log info;   # debug プローブ時のみ debug

events { worker_connections 64; }

http {
    access_log off;
    client_max_body_size 200m;
    client_body_buffer_size 1k;
    client_body_temp_path __PREFIX__/tmp/client;
    proxy_temp_path       __PREFIX__/tmp/proxy;
    fastcgi_temp_path     __PREFIX__/tmp/fastcgi;
    uwsgi_temp_path       __PREFIX__/tmp/uwsgi;
    scgi_temp_path        __PREFIX__/tmp/scgi;

    server {
        listen 127.0.0.1:18452 ssl sndbuf=64k;
        ssl_certificate     __PREFIX__/certs/cert.pem;
        ssl_certificate_key __PREFIX__/certs/key.pem;
        ssl_protocols       TLSv1.3;

        location / {
            proxy_pass http://127.0.0.1:<backend>;
            proxy_http_version 1.1;
            proxy_request_buffering off;
            proxy_buffering off;
        }
    }
}
```

証明書は自己署名 (openssl req -x509) で chmod 644、キーは chmod 600。

## 再現シナリオ

1. backend モックはリクエストヘッダ受領後ただちに 16MB の応答を流し
   (select ベースのノンブロッキング送受信で body も読み捨てる)。
2. クライアントは TLS1.3 で `POST /upload` (Content-Length 100MB) を
   送信し、`SO_RCVBUF=4096` + `TCP_WINDOW_CLAMP=4096` でサーバからの
   応答を読み続けない → nginx のクライアント向け SSL_write が
   WANT_WRITE でブロックする。
3. クライアントは SSL_key_update() で TLS1.3 KeyUpdate
   (update_requested) レコードを注入する。
4. body の送信を再開すると、nginx の body 読取中の SSL_read() が
   KeyUpdate 応答の書き込みを必要とし `SSL_ERROR_WANT_WRITE` →
   1.31.8 は無限ループ (utime 激増)、1.31.9 は明示 NGX_AGAIN 処理で
   イベントループへ戻る、という差が出ることを期待する。
5. 判定: worker の `/proc/<pid>/stat` の utime+stime を 2 秒窓で計測し、
   `delta >= 0.75 × 窓 × CLK_TCK` (2 秒窓で 150 tick) で SPIN 判定。

### タイミングパターン (1 試行あたり 10 秒以内)

| パターン | 内容 |
|---|---|
| p1-ku_with_body | 受信拒否 → body chunk → 0.5s → KeyUpdate+body を同一 TCP 送信 |
| p2-ku_alone_then_body | KeyUpdate 単体送信 → 0.2s → body 再開 |
| p3-partial_read_then_ku | 応答ヘッダを一部読み出してから KeyUpdate+body |
| p4-ku_immediate_with_body | ヘッダ直後に即 KeyUpdate+body |
| debug-probe | error_log debug で同一シナリオ、want write 出現回数を計測 |

- `SSL_read: want write` (ngx_ssl_recv の WANT_WRITE 分岐の debug 文字列):

- body 読取中の `SSL_get_error`: 常に `2` (SSL_ERROR_WANT_READ)。

- `http client request body recv` 19 件 (うち NGX_AGAIN=-2 を含む)。
  body 読取ループ自体は正常にイベントループへ戻っている。

## 結論: 再現可否

未再現 (挙動差なし)。4 種のタイミングパターン × 4 バイナリ
(1.31.8 / 1.31.9 / 両 ASan 版) で worker utime の増分はすべて 0.0 で
あり、CPU スピンは検出できなかった。vuln と fixed で挙動差は観測され
なかった。

### 到達できなかった理由の分析

1. トリガ条件 (読取経路の WANT_WRITE) が発生しなかった: debug ログ
   で body 読取中の `ngx_ssl_recv()` は常に `SSL_ERROR_WANT_READ`
   (SSL_get_error: 2) を返しており、WANT_WRITE は一度も現れなかった。
2. OpenSSL 3.0.22 のレコード層の挙動: 応答 KeyUpdate の送出は
   SSL_read の処理中に即時書き込まれるのではなく、保留中の SSL_write
   (wpend) の完了タイミングに紐づく。本試行では応答書き込みが
   WANT_WRITE でブロックされたまま (`SSL_write: -1` ×22) なので、
   KeyUpdate 応答の書き込み機会が「ソケットが書けるようになった時」
   (= write イベント) に先送りされ、body 読取中の SSL_read が
   WANT_WRITE を返する状況が作れなかった。アップロード版参照実装
   (OpenSSL 4.1) の「NST/KeyUpdate 書き込みが wpend に阻まれて延期
   される」という分析と整合する。
3. 書き込み側のブロック自体は成立: `SSL_write: -1` が 22 回観測
   されており、「クライアントが応答を読まない → nginx の SSL_write が
   WANT_WRITE」という前半条件は再現できている。不足しているのは
   「body 読取中の SSL_read が WANT_WRITE を返す」後半のみである。
4. アップロード版 (OpenSSL 4.1, 400 通り以上の組み合わせ) も同様に
   FAIL であり、本環境の OpenSSL 3.0.22 ビルドでも 4 パターン + debug
   プローブで差が出なかった。OpenSSL のバージョン差によるレイヤ挙動
   (1.1.1 系などで SSL_read 内の KeyUpdate 応答即時書き込みが行われる
   ケース) を突けば到達できる可能性は残るが、今回のビルドセット
   (OpenSSL 3.0.22 固定) では「挙動差なし」として正直に記録する。
