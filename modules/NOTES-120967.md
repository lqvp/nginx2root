# CVE-2026-120967 — stream の SNI 指定時クライアント証明書検証漏れ 再現ノート

## 1. 概要

- 対象: nginx 1.31.8（脆弱） / 1.31.9（修正）、stable 1.30.6（脆弱） / 1.30.7（修正）
- 不具合: stream のバーチャルサーバ + SNI 構成（default サーバ = `ssl_verify_client off`、
  SNI サーバ `sni.example` = `ssl_verify_client on`）で、SNI コールバックが走った
  「最初の `ngx_stream_ssl_handler()` 呼び出し」の中で `SSL_do_handshake()` が 1（完了）を
  返した場合（同期完了）、クライアント証明書の検証がハンドラ先頭で取得した
  default サーバ側の sscf（verify off）で行われてしまう。結果、SNI サーバの
  `ssl_verify_client on` が適用されず、無効なクライアント証明書 / 無証明書の接続が
  上流まで通過してしまう（検証漏れ）。
- 修正コミット: `6f9fcee` "Stream: client SSL certificates were not checked with SNI"
  （ハンドシェイク完了後に sscf を取り直す 2 行。stable-1.30 へは `77f90f1c` として
  バックポート）
- 検証漏れ系（認証バイパス）のため、本モジュールの判定は挙動差ベース。

### 1.1 脆弱性の仕組み

1. `ngx_stream_ssl_handler()` はハンドラ先頭（= default サーバ）で `ngx_stream_ssl_module`
   の設定 `sscf` を取得する。
2. ClientHello に SNI が含まれる場合、OpenSSL の SNI コールバック（サーバ選択）が
   `SSL_do_handshake()` 内で呼ばれ、仮想サーバ `sni.example` が選択される。
3. この最初の `ngx_stream_ssl_handler()` 呼び出し内でハンドシェイクが完了（同期完了）
   すると、その直後のクライアント証明書検証は依然として default サーバの sscf
   （`ssl_verify_client off`）で実行されるため、SNI サーバの検証が効かない。
4. 修正版はハンドシェイク完了後に sscf を再取得するため、`sni.example` の
   `ssl_verify_client on` が適用され、無効証明書は検証失敗で切断される。

同期完了が発生するかどうかは OpenSSL の内部タイミング（イベントループへの再入が
発生するか）に依存する。参照実装（アップロード版）では OpenSSL 4.1 では初回呼び出し
でのハンドシェイク完了が観測できなかったと報告されている。

証明書は `openssl req/x509` で module が毎回生成（chmod 644）:
CA1（正規系: サーバ 2 種と client-good の発行元）と CA2（無効証明書 client-bad の

## 3. 設定（モジュールが毎回生成）

`poc-run-G/120967/nginx.conf` の要点:

```nginx
worker_processes 1;
daemon on;
pid <rundir>/nginx.pid;
error_log <rundir>/logs/error.log debug;   # ← SSL_do_handshake 呼び出しシーケンスを記録

events { worker_connections 256; }

stream {
    server {                                # default サーバ = 検証なし
        listen 127.0.0.1:18450 ssl;
        server_name default;
        ssl_certificate     <certs>/server-default.pem;
        ssl_certificate_key <certs>/server-default.key;
        ssl_verify_client off;
        proxy_pass 127.0.0.1:19012;
    }
    server {                                # SNI サーバ = 検証あり
        listen 127.0.0.1:18450 ssl;
        server_name sni.example;
        ssl_certificate     <certs>/server-sni.pem;
        ssl_certificate_key <certs>/server-sni.key;
        ssl_verify_client on;
        ssl_client_certificate <certs>/ca1.pem;
        proxy_pass 127.0.0.1:19012;
    }
}
```

上流（19012）は Python スレッドの echo サーバで、到達すると `POC-BACKEND-OK` を
返す（= 検証バイパス発生の検知用）。

## 4. トリガ手順（クライアントバッテリ）

`modules/120967.py` 内のクライアント群（すべて `server_hostname="sni.example"`）:

- async: 通常の `SSLSocket`（Python ssl モジュール）。no-cert / bad-cert × TLS1.2/1.3。
- sync（擬似同期）: `ssl.MemoryBIO` + poll で読み書きを交互に行い、ClientHello を
  1 セグメントで渡し切る実装。`split=64`（send 分割）/ `mss=1400`（TCP_MAXSEG）/
  `appdata_early`（先行アプリデータ）のバリエーション。
- resume: `openssl s_client -reconnect` によるセッション再開。
- ctrl: 正規証明書 `client-good`（検証が通ることの対照実験）。

判定: no-cert / bad-cert の接続が上流 echo まで到達（ACCEPT）したら検証バイパス発生
→ `effect=TRIGGERED, trigger=True`。

## 5. 実行結果（`modules/120967.result.json`）

### 6 バイナリ（1.31.8 / 1.31.9 / asan 両方 / 1.30.6 / 1.30.7）: すべて VERIFIED

```
vuln       1.31.8 → VERIFIED, trigger=False
fixed      1.31.9 → VERIFIED, trigger=False
asan-vuln  1.31.8 → VERIFIED, trigger=False
asan-fixed 1.31.9 → VERIFIED, trigger=False
vuln1306   1.30.6 → VERIFIED, trigger=False
fixed1307  1.30.7 → VERIFIED, trigger=False
```

全バイナリで同一結果:

- 無効証明書 / 無証明書 + SNI=sni.example の全試行（10 件）は検証エラーで切断
  （`REJECT-data` = TLS alert `bad certificate` 等）。
- 正規証明書は通過（`ctrl_good-cert_tls12/13 = ACCEPT`）→ 検証機構自体は有効。
- 接続 17 件すべて 2 回以上の SSL_do_handshake 呼び出しで完了
  （first-call 完了 0 件）→ 同期完了が発生しなかった。

理由: 本環境のビルドは OpenSSL 3.0.22 を使用しており、最初の
`ngx_stream_ssl_handler()` 呼び出し内でのハンドシェイク完了（同期完了）が
ClientHello を 1 セグメントで渡し切る擬似同期クライアントでも発生しない。
このため非同期経路（2 回目以降の呼び出しで完了 → SNI 選択後の sscf で検証）に
なり、脆弱版（1.31.8 / 1.30.6）でも検証バイパスは発生しなかった。
アップロード版参照実装の「OpenSSL 4.1 では同期完了が観測できず未観測」という
報告と整合する（OpenSSL のバージョン/設定によって同期完了の可否が変わる）。

### probe_emulation（プローブビルドによる同期完了エミュレーション）: 挙動差を実証

`poc-run-G/120967/probe/sbin/nginx`（1.31.8 に環境変数スイッチで計装を追加した
プローブビルド）で、同期完了が起きた場合の挙動をエミュレーション
（fact #612 で実証済みの内容と同一手順・同一結果）:

| モード | 環境変数 | no_cert | bad_cert | good_cert |
|---|---|---|---|---|
| natural_async | （なし） | REJECT | REJECT | ACCEPT |
| emul_sync_vulnerable | `NGX_PROBE_EMUL_SYNC=1` | **ACCEPT** | **ACCEPT** | ACCEPT |
| emul_sync_fixed | `NGX_PROBE_EMUL_SYNC=1` + `NGX_PROBE_SYNC_FIX=1` | REJECT | REJECT | ACCEPT |

- `NGX_PROBE_EMUL_SYNC=1`: 初回ハンドラ呼び出しの sscf を ctx に保存して再入時に
  再利用する（= 同期完了時の default サーバ側 sscf の利用をエミュレート）。
  → 無効証明書 / 無証明書がそのまま上流へ通過（検証バイパス）= 脆弱版 1.31.8
  で同期完了が発生した場合の挙動。
- `NGX_PROBE_SYNC_FIX=1` 追加: 修正版（1.31.9）相当（ハンドシェイク完了後に sscf を
  再取得）。→ 無効証明書は REJECT に戻る。

これにより「初回 handler 呼び出し内で SSL_do_handshake が完了すれば、脆弱版は
SNI サーバの `ssl_verify_client` を迂回する」という本 CVE の成立条件が本環境
（OpenSSL 3.0.22）でも実証された。修正版が同期完了時に検証を行うことも
`NGX_PROBE_SYNC_FIX=1` で確認済み。

## 6. 判定ロジック（modules/120967.py）

- no-cert / bad-cert + SNI の接続が上流 echo に到達（ACCEPT）→ TRIGGERED, trigger=True
- 同期完了が発生せず（error.log の SSL_do_handshake 呼び出しシーケンス解析:
  first_call_complete=0）、全試行が REJECT、正規証明書が ACCEPT
  → VERIFIED, trigger=False（検証機構は有効、同期完了は環境依存のため未発生）
- `nginx -t` 失敗 → SKIP、起動失敗 → ERROR

## 7. 備考 / 限界

- 本 CVE は OpenSSL の内部タイミングに依存するため、実バイナリ 6 種では同期完了が
  発生せず effect=VERIFIED となった。同期完了時の挙動差はプローブビルドによる
  エミュレーション（`probe_emulation` セクション）で実証している。
- 1.30.6 / 1.30.7 にも当該コードパスがある（`77f90f1c` バックポート対象）ため
  6 バイナリすべてで検証している。
- `pkill` 不使用。master PID（pid ファイル）を保持して SIGQUIT → SIGKILL で停止。
- 証明書はすべて chmod 644。
