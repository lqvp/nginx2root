# CVE-2026-123634 — resolver の UAF（mirror サブリクエスト） 再現ノート

## 1. 概要

- 対象: nginx 1.31.8（脆弱） / 1.31.9（修正）
- 不具合: `ngx_resolver_process_a()` が名前解決の待ちリストを走査する途中で、
  「現在処理中ではない別の resolve ctx」が解放され、走査が解放済み ctx を
  使ってしまう use-after-free。
- 誘発条件: upstream の名前解決で、同じ名前を解決中のサブリクエストが 1 つ以上あり、
  かつ upstream の resolve handler の中からリクエストが terminate されること。
- 修正コミット: `e39708e` "Resolver: fix non-current resolve finalization from resolve handler"
  （`ngx_resolve_name_done()` で他 ctx を即 free せず `free_handler` 経由に変更）

### 1.1 ソース上の根拠（1.31.8）

`src/core/ngx_resolver.c` の NXDOMAIN 処理（抜粋）:

```c
    next = rn->waiting;
    rn->waiting = NULL;
    ...
    while (next) {
        ctx = next;
        ctx->state = code;
        ctx->valid = ngx_time() + ...
        next = ctx->next;
        ctx->handler(ctx);      /* ← handler の中で別 ctx が free され得る */
    }
```

`ngx_resolve_name_locked()` で 2 つ目の ctx は待ちリスト先頭に挿入される（LIFO）:

```c
            last->next = rn->waiting;
            rn->waiting = ctx;
```

そのため「先に登録された main」が後ろ、「後から登録された mirror」が先頭になる。
本再現では POST の本文送信を遅らせ、mirror サブリクエストが先に解決を開始し、
本文受信後に main が同じ名前を解決待ちに加わることで、待ちリストを
`[main, mirror]` の順（main が先頭）にしている。

```nginx
    server {
        listen 127.0.0.1:18445;

        location / {
            mirror /mirror;
            mirror_request_body off;
            proxy_pass http://$host:19000;
        }

        location = /mirror {
            internal;

        }
    }
```


## 4. 再現手順

1. DNS サーバ（15353/UDP）はクエリ受信から 20ms 後に NXDOMAIN を返し、
   直後にそのクライアント socket を `SO_LINGER(1,0)` で RST する。
2. クライアントは `POST / HTTP/1.1` + `Host: u<N>.test` + `Content-Length: 8` を
   ヘッダだけ送る。
   - `mirror_request_body off` のため mirror サブリクエストは本文を待たず、
     この時点で `u<N>.test` の解決を開始する（待ちリスト 1 個目）。
3. 2ms 後に本文 8 バイトを送る。
   - 本文受信が完了してから main の upstream init が走り、同じ `u<N>.test` を
     解決待ちに追加する。LIFO のため待ちリストは `[main, mirror]` になる。
4. 20ms 後に DNS が NXDOMAIN を返す。resolver は待ちリストを切り離してから
   先頭（main）の handler を呼ぶ。main は 502 を書こうとするが、クライアントは
   同時刻に RST しているため `writev()` が `104: Connection reset by peer` で失敗。
   → `ngx_http_terminate_request()` が main の cleanup を実行。
5. main の cleanup は mirror の upstream cleanup も含むため、
   mirror の resolve ctx に対して `ngx_resolve_name_done()` が呼ばれる。
   すでに待ちリストから切り離されているので 1.31.8 は
   `[alert] could not cancel u0.test resolving` を出して ctx を free。
6. resolver の走査は `next`（= 解放済み mirror ctx）へ進み、
   `ctx->state = code` の書き込みと `ctx->handler(ctx)` 呼び出しで UAF。
7. 1.31.9 では同じ経路を踏むが、free は `free_handler` 経由に遅延されるため
   クラッシュしない。

## 6. モジュールの使い方

```bash
python3 modules/123634.py build/inst-vuln/sbin/nginx  poc-run-B
python3 modules/123634.py build/inst-fixed/sbin/nginx poc-run-B
```

`run(binary, workdir, host="127.0.0.1")` は `{"cve","configured","trigger","effect","detail"}`
を返す。`effect` の判定:

- `CRASH`: `worker process N exited on signal 11` / `segmentation fault`
- `UAF`: `[alert] could not cancel` があり、クラッシュは無い（解放済み ctx の再利用）
- `TRIGGERED`: 同一経路を実行したが `could not cancel` は `[debug]` のみ、または未検出
- `ERROR` / `SKIP`: 起動失敗 / `nginx -t` 失敗（モジュール不足など）

結果ファイル: `modules/123634.result.json`（1.31.8 / 1.31.9 の両方）。

## 7. 注意点

- 実時間レースのため、DNS 応答と RST を「同一 I/O バッチ」に載せる必要がある。
  本手法では DNS 応答直後に同じスレッドで RST するため安定して成立する。
- `valid=1s` により同一名の 2 回目以降はキャッシュに当たる。1 リクエストごとに
  異なる Host 名（`u0.test`, `u1.test`, ...）を使っている。
- worker がクラッシュすると master が自動再起動する。停止は pid ファイルの master に
  `SIGTERM`、加えて `/proc` 走査で自 prefix の nginx のみを対象にする（pkill 不使用）。
